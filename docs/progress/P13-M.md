# P13-M：行业相对强弱（数据可行性与 PIT 审计）

## 目标

在 P13-I～P13-L 连续未发现稳定增量后，测试不同的信息维度：个股相对于其历史上当时所属行业的表现，是否包含超出通用市场/个股技术因子的增量信息。

本阶段不把当前行业标签套到历史数据，而是先建立历史行业归属的 point-in-time（PIT）契约。

## 数据审计结论

仓库现有 scripts/data_layer.py 中的 stock_sector_spot / 行业板块实时数据属于实时采集与缓存层，不能作为历史行业归属回测数据。

当前本地历史数据只有股票日线与三个市场指数，没有历史行业成员关系表。因此获得 PIT 行业成员数据前，不进入 OOS 因子实验。

## 候选数据源

Tushare 的 index_member_all 提供申万三级分类的股票成分，并返回 in_date / out_date，可按股票代码查询所属分类。

项目采用以下保守约定：

- effective_from = in_date 00:00 +08:00
- effective_to = out_date 00:00 +08:00
- available_time = effective_from 当日 16:00 +08:00
- source_type = vendor_effective_date

available_time 是项目的保守 PIT 安全约定，不是 Tushare 的实际发布时刻。

Tushare 的 bak_basic 从 2016 年开始提供按交易日的 industry 字段，可作为交叉核验来源，但其行业字段口径与申万分类不同，因此不与申万行业混用。

## 当前实现

- src/astock_v2/industry.py：行业归属 PIT 数据契约、可用性选择、重叠区间检查。
- tests/test_industry.py：4 个 PIT/区间测试。
- scripts/import_tushare_industry_membership.py：从 Tushare 导出指定股票的申万历史行业归属。

## 验收前提

只有同时满足以下条件，才允许进入 P13-M OOS：

1. 8 只股票均能取得历史行业归属；
2. 每个归属区间通过无重叠检查；
3. 决策日只使用当时已生效且 available_time <= decision_time 的归属；
4. 行业收益使用当时行业成员，而不是今天的成员；
5. 行业价格/收益数据同样满足 PIT 条件；
6. 不读取 realtime cache；
7. 用户本地数据不提交 GitHub。

## 实验设计

基线保持 P13-I～P13-L：

- train=252
- test=20
- step=20
- gap=1
- train-rate baseline
- Brier / Log Loss 主指标
- Accuracy 辅助指标

候选：

- industry_relative_return_5
- industry_relative_return_20

先固定申万一级行业，避免三级行业过细造成小样本和高方差。

只比较：

- baseline
- baseline + industry relative 5/20d

如果仍无稳定增量，则停止继续堆叠技术类因子，转向基本面 / 事件信息层。

## 当前人工动作

本阶段现在唯一需要用户参与的是提供 Tushare 访问权限并在本地运行导入。Token 不要写入仓库。

PowerShell：

    $env:TUSHARE_TOKEN="你的token"

然后：

    python scripts/import_tushare_industry_membership.py --symbol 000001 --symbol 000333 --symbol 000651 --symbol 002594 --symbol 300308 --symbol 600036 --symbol 600519 --symbol 601318

默认输出：

    data/industry/tushare_sw_membership.csv

该 CSV 不提交 GitHub。

## 重要说明

P13-M 当前完成的是数据契约与可行性审计，不是因子有效性结论。即使行业相对强弱未来出现效果，也必须通过多股票、多时间块的严格 OOS 验证后才能进入模型。
